What it is

Monitoring is only the beginning.

The problem

Computers slow down gradually: CPU pressure, memory pressure, heavy swap use, storage bottlenecks, background applications, resource contention, and CPU throttling where the platform exposes enough information. Utilisation percentages alone do not show how real work performs.

DESKFLOW is a device-care utility. It is not an antivirus or malware scanner.

Ordinary monitors show utilisation and processes. DESKFLOW adds a measured probe, a per-machine baseline, a 20-second prediction, a cause estimate and a re-measurement after a fix.

The approach

  1. Telemetry. CPU, memory, disk and process data.
  2. Controlled measurement. A fixed CPU, memory and disk probe.
  3. Feature engineering. Rolling windows into numbers.
  4. Inference. Regression, classification, anomaly detection.
  5. Health score. Derived from predicted slowdown.
  6. Issue identification. Likely cause with evidence.
  7. Safe remediation. Previewed, confirmed, logged.
  8. Post-fix validation. Measure again, report honestly.

Architecture

From raw telemetry to an actionable diagnosis.

Select a stage or press Play. The packet follows the same path a real scan takes.

Source modules

Windows and macOS expose different system capabilities, so common code reaches them through the platform package. ML libraries are imported lazily so the CLI stays light and runtime measurements are not disturbed by model loading.

Telemetry and probes

Measure the machine. Do not just observe it.

System telemetry

Sampled every 2 s: CPU utilisation and frequency where reliable, memory and swap, disk activity, process data, and power state. A capability the platform does not expose is marked unavailable, not recorded as zero.

Performance probes

Every 4 s DESKFLOW times a fixed CPU loop, memory allocation and disk write with a high-resolution clock. The workload must stay identical between data collection and live inference, or the baseline comparison becomes meaningless. Background activity adds noise, so calibration and a stability check run first.

Separate baselines for battery and AC

Laptop performance changes with power state, so each state has its own healthy baseline, and a result is only compared with the baseline for the state it was measured in. The CLI checks baseline age and drift and offers recalibration.

Machine learning

Different algorithms. Different responsibilities.

Telemetry becomes a numeric feature row: 6 s and 12 s rolling windows over CPU, memory, swap, disk, probe ratios, process and thread counts. The design spec lists 27 features. Features use past data only, and the same builder serves training and live inference.

TaskQuestionModelsBaselines
RegressionHow slow will the probe be in 20 s, relative to this machine’s baseline?Ridge (L2-regularised linear), Random Forest (averaged trees), XGBoost (boosted trees)Persistence (same as now), Rolling Mean. Not trained models.
ClassificationWhich cause is likely: healthy, CPU, memory, disk or background load?Logistic Regression, Random Forest, XGBoostMajority-class
Anomaly detectionIs this state unusual compared with healthy behaviour?Isolation Forest, fitted on healthy rows onlyNone

Classification chooses among known causes. Anomaly detection flags unusual behaviour without naming a cause. Primary models are chosen by grouped cross-validation, recorded in the model card, and no model is assumed to win.

Health score

Score = 100 at a predicted ratio of 1.0× or less, falling linearly to 0 at 3.0×. Move the slider.

The score is ML-derived. Memory, storage and background-app status are shown as measured readings, not as separate predictions. Contributing factors come from XGBoost’s built-in contributions.

Training

Training is a process, not a button.

Data comes from controlled lab scenarios and normal use on real machines. Whole sessions are held out, tuning uses grouped cross-validation by run, preprocessing is fitted on training data only, and the test set is touched once.

Model Lab

Which model predicts better? Let the measurements decide.

Results are read from data/project-data.json, generated from the model card and report data. A synthetic model never shows metrics. A model is called better than Persistence only when the 95% bootstrap interval of the improvement excludes zero.

Metrics

MAE: average absolute error; lower is better. RMSE: penalises large errors more. R²: share of target variance explained; not an accuracy percentage.

Live verification

Every model predicts at time t, the machine keeps running, and about 20 s later a new probe measures the truth. Fewer than 30 resolved pairs cannot rank models. Held-out evaluation and live verification are reported separately.

Fix Center

Diagnosis is useful only when action is safe.

Planned actions per the Phase 10 spec (confirm each against the code): clean temporary files, clean supported caches, empty recycle bin or trash, trim memory where supported, close idle applications, end selected heavy tasks.

Safety mechanisms

  1. Dry-run preview
  2. Explicit confirmation; typed confirmation for CAUTION actions
  3. Protected processes and parent-process protection
  4. Current-user processes only
  5. Allowlisted cleanup directories, symlink protection
  6. Audit log

Verify the result

  1. Initial scan
  2. Fix inventory
  3. User selection
  4. Safety check
  5. Execution
  6. Wait and re-sample
  7. Before and after comparison

Closing applications can lose unsaved work. Memory trimming can be temporary. DESKFLOW never promises recovered space in advance, and reports it honestly when the score does not improve.

Privacy and limits

Designed to inspect locally. Not to transmit.

Privacy

Measurements and models stay on the machine. No private data is sent to a remote ML service.

Limitations

Targets Windows and macOS only. GPU workloads are outside the prediction scope. Results depend on data quality and diversity; a model trained on one machine has limited evidence for others. Power management and background activity affect probe stability. A synthetic model is a demonstration, not validation.

FAQ

What does it predict?

The probe slowdown ratio about 20 seconds ahead.

Why several regression models?

To compare them on the same data and against Persistence, instead of assuming one wins.

Does it use Kaggle data?

No. Data is collected on real machines.

What does DEMO MODEL mean?

The bundled model was trained on synthetic data. It shows the pipeline, not real accuracy.

Will the score always improve after a fix?

No. DESKFLOW measures again and reports what it finds.
